# Maagent 开发复盘与接手记录

日期：2026-10-17。基线提交：`090e428`。依据：桌面《maagent_项目说明与开发过程》、仓库历史、当前源码与项目开发技能。本次为首轮定向检查，并非所有模块的完整审计。

## 开发过程复盘

1. 从 GameOps / MAA 单软件闭环起步，明确“调度已有软件”的产品定位；GUI 操作替代直接接管 MaaCore，降低了重复实现游戏任务的成本。
2. 周常、月常、报告与桌面 UI 增长后，抽出了 BaseWorkflow、状态与控件模块。这些抽象仍有价值，应该继续复用。
3. 接入 MaaEnd 时发现不同窗口技术和权限边界，形成“API + 热键 + 日志”的组合；后来 BetterGI 又需要全窗口 OCR、区域过滤与日志文件监控。三个软件的控制层确实存在差异，不宜强行合并截图和点击实现。
4. 工作流、定时、账号、远程控制逐步汇合到 WorkflowController，GUI 和 PWA 共享执行状态，是后续扩展的合适入口。
5. 手机方案已经转向 PWA；Flutter 工程留作历史方案。对话 agent 为另一条实验路线，尚未接入统一日常控制。当前应优先巩固主流程与回归验证。
6. 最近集中修复 MAA 完成误判、MaaEnd 启动时序以及 BetterGI OCR，说明最容易出现回归的是外部软件行为、日志边界和运行状态判断。

桌面记录的阶段编号不是严格时间排序（第 7 阶段日期早于第 6 阶段）；应以 Git 历史及实际源码判断实现状态。项目技能中也仍有已删除的 workers.py、pipeline_override 等旧描述。

## 建议后续开发顺序

1. 实机验收 BetterGI：正常完成、手动急停、周常配置是否被页面重新加载；跨午夜的 ExecutionRecords 当前只读结束当天文件，值得补多日期汇总测试。
2. 调度边界：当前补跑窗口使用同一自然日的分钟差，跨午夜补跑尚未覆盖；核对凌晨 4 点附近的去重与“下次运行”提示，并先确定期望行为。
3. 控制器可靠性：报告追加与清空的磁盘操作尚未一起纳入锁范围；异常后的状态呈现和运行期间配置快照也值得单独处理。
4. 远程服务：梳理本机所有者与其它注册账号的控制权限、登录限流、长连接事件队列上限及令牌撤销后的连接行为，分别形成回归测试。
5. 将对话 agent 接入统一 WorkflowController 前，先界定可执行动作、停止语义与确认流程，避免出现第二套调度和报告链。
6. 确定 Flutter 是否永久退出路线后，再决定移入归档或删除；后续按功能拆分较大的 gui/app.py。

发布应使用 `maagent.release.spec`（内置干净配置）。旧技能中的命令嵌入个人 config/config.yaml，不适合作为分发构建命令。个人配置与导出会话仍禁止提交。
